What is the base package?

A quick orientation for newcomers

The short version

The base package is a collection of markdown files in a GitHub repo. These files contain content guidelines (rules, patterns, terminology, and examples) that AI tools use to help people write great UI content for Microsoft Security products.

Think of it as a reference library that AI tools consult. When a content designer asks an AI tool to "write an error message for Sentinel," the tool checks our guidelines to make sure the output follows Microsoft voice, uses the right terms, meets accessibility standards, and matches the security tone.

Who's involved?

Our team (authors)
We write and maintain the guideline files. We decide what the rules are, keep them current, and ensure they align with Microsoft style guides.
Tool builders (integrators)
Engineers, UX designers, and content designers who build the skills, agents, and plugins that CONNECT to our guidelines. They wire the plumbing so AI tools can find our files.
Users
Any partner who uses AI tools (GitHub Copilot CLI, GitHub Copilot, Figma, etc.) and benefits from our guidelines without needing to know how the system works.

Glossary

Every term in the system, explained in plain language.

📦 The package (what we deliver)

Base package

The complete set of content guidelines we deliver. A collection of markdown (.md) files stored in a GitHub repo. Contains both general and AI-specific guideline files.

Think of it as a reference library that AI tools consult when writing UI content.

General guidelines

General guidelines that apply to ALL UI content regardless of whether AI is involved. Covers: voice & tone, terminology, naming, UI copy, accessibility, localization, marketing messaging, and more.

These are the "always loaded" default layer. Every request starts here.

AI files

Guidelines that apply ONLY when the UI involves AI, Copilot, or agents. Covers: AI tone adaptations, agent naming, responsible AI guardrails, failure patterns, agent UX, and more.

Self-contained: everything needed for AI content in one place. Loaded on demand, not for every request.

Frontmatter

A small metadata block at the top of each .md file written in YAML format (between --- markers). Contains: title, type, tags, version, scope.

Helps tools identify what a file is about and whether it's relevant to the current task.
⚙️ The plumbing (how guidelines get delivered)

Skill

A small file (SKILL.md) that defines one capability, like "UI Writing" or "Terminology Vetting." It doesn't contain guidelines itself; it tells the system which guidelines to fetch for that task.

Like a recipe card that lists ingredients to gather, not the ingredients themselves.

Loader

The engine that fetches the right guideline files. Takes a request like "I need voice & tone guidelines for Sentinel," reads the manifest, and returns the matching files. It's a simple fetch script: no merging logic, no priority decisions.

Like a librarian who pulls the requested books off the shelf. They don't decide which book is more important: that's the skill's job.

Orchestrator

The traffic cop that receives a request and decides which skill to activate. When someone asks "write me an error message," the orchestrator routes to the UI Writing skill.

It picks the right workflow. The skill then tells the loader what to fetch.

Package index (manifest.yaml)

A per-folder table-of-contents file. Lists what guideline files that folder contains, their categories (terminology, voice-tone, etc.), and routing rules. The loader reads these to find files without scanning the whole repo.

Not an agent manifest. It's just a table of contents for each folder.

Precedence chain

The rule for which guidelines "win" when multiple layers have overlapping content: Subarea > Area > Horizontal > Base. Most specific wins.

If Sentinel defines "alert" differently than Base, Sentinel's definition wins for Sentinel tasks.

Cross-reference trigger

A note in the general guidelines that says: "If this task involves AI/Copilot/agents, also load the AI files." This is how AI guidelines get pulled in without being loaded for every single request.

Like a library cross-reference card: "See also: AI section."
🌐 The infrastructure (how AI tools connect)

MCP (Model Context Protocol)

A standard that lets AI tools ask external servers for information at runtime. Any AI tool with MCP support can connect to any MCP server: it's a universal adapter.

The universal plug that connects AI tools to knowledge sources like ours.

Design-system MCP server

The specific MCP server that indexes .md files from repos across Microsoft. Our guidelines have their own knowledge base there.

The main highway most AI tools use to reach our guidelines today.

YAML frontmatter

Structured metadata at the top of each .md file (between --- markers). Contains fields like title, type, tags, and scope. Parsers read this to build searchable indexes without opening the full file.

Like a library catalog card stapled to the front of a book. Tools scan these to know what's inside without reading the whole thing.

Parser

The component inside the design-system MCP server that reads files and builds a searchable database. Optimized for .md files. Ignores .yaml if no .md version exists.

This is THE technical reason we convert everything to markdown. The Parser can't read YAML.

MCP index

The searchable database the Parser builds after reading our .md files. We don't create this: it's built automatically when the Parser processes our repo.

Different from our Package Index. This one is auto-generated; ours is hand-authored.

AI tools (consumers)

The tools partners use that consume our guidelines: GitHub Copilot CLI, GitHub Copilot, VS Code Copilot, PR assistant tool, Figma plugin, M365 Copilot, custom agents.

These are the "customers" of our base package. We write guidelines; they use them.

End-to-end workflow

How guidelines go from our repo to the partner's screen. Two phases: setup (one-time) and usage (repeatable).

🔧 Phase 1: Setup (one-time, someone builds the connection)

Before any partner can get AI-assisted content, someone needs to build the tool or connection that hooks into our base package. This happens once per tool, not per request.

0

A tool builder creates a connection to our package

Someone on our team or a partner team builds a skill, agent, plugin, or tool configuration that points to our base package files. This is the prerequisite: without it, AI tools have no context into our guidelines.

Examples already built:
• Figma plugin: built by a security UX designer, pointing to our package folder
• PR assistant tool: pull request tool using our content skill to provide revisions for string check-ins
• GitHub Copilot CLI skills: SKILL.md files, built for our solution partner teams, that call the loader to fetch guidelines on demand
• Agent 365 messaging skill: Decision framework for in-product Agent 365 messaging in Microsoft Security portals

🔄 Phase 2: Usage (repeatable, user gets help)

Once a connection exists, partners can use it repeatedly. Here's what happens each time.

1

User makes a request

Someone uses a connected AI tool and asks for help with UI content.

Example: "Write an error message for when a Sentinel data connector fails to authenticate."
↓
2

AI tool accesses our guidelines

The tool connects to our base package through one of the established paths:

Path A: Design-system MCP server, Parser has already indexed our .md files; tool queries the knowledge base
Path B: Direct repo read, GitHub Copilot reads .md files directly from the repo
Path C: Our MCP server (future), Loader resolves files and returns merged content
↓
3

Orchestrator routes to the right skill

Based on what the user asked, the system activates the appropriate capability:

→ UI Writing (generate strings) | → Terminology Vetting (check terms) | → Content Evaluation (review quality) | → Readability Analysis (check grade level)
↓
4

The skill calls the loader

The skill says: "I need guidelines for area=sentinel, subarea=graph, workflow=ux-writing." The loader reads Package Index/manifest files to determine which .md files are relevant.

↓
5

Loader fetches and delivers files

The loader reads the manifest and returns matching .md files. It's a simple fetch: no logic, no filtering, no decisions about priority.

Loader reads manifest → finds relevant files for the requested area/subarea/workflow → returns them all to the skill.
↓
6

Skill/LLM agent applies precedence

The skill (or the LLM agent itself) layers files by specificity. Most specific wins when there's overlap:

BASE (always) → HORIZONTAL (if AI context, via cross-reference trigger) → AREA (product) → SUBAREA (most specific)
Example: Sentinel/Graph terminology overrides Base terminology for Graph-specific terms.
↓
7

AI tool applies the guidelines

The tool uses the merged guidelines to generate or review the content. It validates:

✓ Readability (Flesch-Kincaid < grade 10) | ✓ Correct terminology | ✓ Voice and tone | ✓ Accessibility | ✓ No conflicts
↓
8

User receives trustworthy output

The user gets polished, on-brand UI content they can trust. Output includes generated strings (with tone variants), terminology validation, readability scores, and improvement suggestions.

What's in the package

Two file sets, one deliverable. The base package contains both: they're organized separately so AI tools only load what's relevant.

📄 General guidelines

These files load for EVERY request (the default layer)
  • Voice & tone (Microsoft's 3 voice principles)
  • Security voice & tone (how our admin audience differs from standard voice guidance)
  • Microsoft terminology (approved terms, definitions, usage)
  • Internal security terms (~300 team-curated terms and definitions)
  • External security terms (industry-standard terms from NIST, CISA, MITRE, and similar sources)
  • Naming guidelines (product and feature names)
  • UI copy guidelines (patterns, do/don't, examples)
  • Error messages (core principles, structure, best practices, UI placement)
  • Navigation labels (information architecture, tooltips, portal-specific guidance)
  • Fluent component guidelines (content guidance for the components used in security UX)
  • Content patterns (wizards, empty states, first-run experiences)
  • Accessibility (screen readers, alt text, WCAG)
  • Localization (string length, placeholders, global readiness)
  • Marketing messaging (legal review rules, claims)
  • Compliance standards & regulations (GDPR, HIPAA, financial and legal requirements)
  • Secure by Design UX patterns (consent, permissions, data handling, security settings)
  • UI tenets & traps (principles, patterns, do/don't examples)
  • Security content design heuristics (rules, product-specific guidance)
  • Security admin personas (core mindsets, pain points, portal-specific best practices)
These files include cross-reference triggers: "If this UI involves AI, Copilot, or agents, also load the AI files for guidance."

🤖 AI guidelines

These files load ONLY when UI involves AI/Copilot/agents
  • AI voice & tone (how tone adapts in AI contexts)
  • AI terminology (AI and agent terms, definitions, terms to avoid)
  • AI naming (how to name agents and AI features)
  • Responsible AI content (guardrails, hedging, human oversight)
  • Failure taxonomy (AI error patterns, trust design)
  • Agent UX patterns (discovery, setup, output flows)
  • Anti-anthropomorphism (don't humanize AI)
  • Anti-sycophancy (don't flatter or over-apologize)
Self-contained: everything needed for AI UI content lives here. Loaded via horizontal opt-in (area manifest declares it) or cross-reference trigger from the general guidelines.

How the layers work together

Precedence: most specific wins

When multiple layers define the same thing (like a term or a voice rule), the most specific layer wins:

SUBAREA (Sentinel/Graph) overrides → AREA (Sentinel) overrides → HORIZONTAL (AI/Agents) overrides → BASE (general guidelines)

Example: If Base says "use 'notification'" but Sentinel says "use 'alert'" for the same concept, then Sentinel's term wins for Sentinel-related tasks.

Common confusion

Terms that sound similar but mean different things. This is a quick reference for when conversations get tangled.

⚠️ "Manifest" vs "Package index"

Industry definition: Manifest = a JSON config file that defines an AI agent's behavior and capabilities. Created by an agent developer.

Our usage: Package index (manifest.yaml) = a per-folder table of contents listing guideline files. It's not an agent manifest: same word, different meaning.

Resolution: When we say "manifest.yaml" we mean our table of contents. When the industry says "manifest" they mean an agent config. Be specific about which one you mean.

⚠️ "Loader" vs "Parser" vs "Orchestrator"

Orchestrator = picks which skill to use (the traffic cop)

Skill = tells loader what to fetch (the recipe card)

Loader = fetches guideline files from the manifest (the librarian: pulls books, doesn't judge them)

Parser = the design-system MCP server's file reader that auto-indexes .md into a searchable database (completely separate system)

Flow: Orchestrator → skill → loader → files → skill/LLM applies precedence. Parser is in a different system entirely (the design-system MCP server).

⚠️ "Package index" vs "MCP index"

Package index = our hand-authored table of contents (manifest.yaml in each folder). We write and maintain it.

MCP index = the design-system MCP server's auto-generated searchable database. We don't write it; it's built from our .md files automatically by the Parser.

We author one (package index). The other (MCP index) is built from our files automatically.

⚠️ "Base package" vs "base layer"

Base package = the FULL deliverable (all files: general guidelines + AI guidelines). This is what we ship to partners.

Base layer = just the general guidelines files specifically. The lowest-precedence layer in the precedence chain.

"Base package" = everything we deliver. "Base layer" = just the general guidelines portion within it.

⚠️ "Instruction" vs "Skill"

After the format change: Instructions = content merged into guideline files (the "what to follow").

Skill = orchestration logic in a SKILL.md file (the "how to load and apply"). Files are pure content; skills handle routing.

Files = content only (no routing logic). Skills = routing only (no content embedded). Clean separation.

⚠️ "Index" (two meanings)

Package index = our authored file (manifest.yaml) listing what guideline files exist per folder. Hand-written by us.

MCP index = auto-built searchable database inside the design-system MCP server. Rebuilt every time the Parser reads our .md files.

If someone says "the index," ask: "do you mean our package index or the design-system MCP server's index?"
